Spec: Resumo Semanal do Pai

Data: 2026-04-02 Elaborado por: @agent-po-missao-da-semana Sprint: Sprint 2 — Comitê de Product Design Escopo: Especificação do que o pai vê ao encerrar a semana. Não é implementação — é especificação para avaliação do comitê. Referência: Recomendação 4 do Resumo Executivo v2 (alta prioridade): “dados do ‘como você se sentiu?’ agregados para o pai”.

Contexto

Hoje não existe tela de resumo semanal. O encerramento da semana acontece silenciosamente — o snapshot é gravado em background (upsertWeekHistory) quando o pai abre o painel, mas nenhuma tela celebra o fim da semana, nenhum dado é apresentado como visão consolidada, e nenhuma ação é sugerida para a semana seguinte.

Esta spec define o que essa tela precisaria conter para fechar o loop de retenção identificado na análise do loop semanal atual.

Quando essa tela aparece

Gatilho: segunda-feira, no primeiro acesso do pai após o encerramento da semana anterior.

Alternativa considerada: domingo à noite com notificação push. Descartada para esta spec — notificações push são sprint dedicada (decisão de produto registrada). O gatilho de segunda-feira é o que pode ser implementado sem infraestrutura de notificação.

Formato: modal de celebração sobre o painel principal, dispensável com 1 toque. Não é tela separada — não quebra o fluxo do pai que quer ir direto às tarefas da semana nova.

Bloco 1 — Dados de Desempenho

O que o pai vê: - Pontuação total da semana por filho (pontos obtidos / pontos máximos possíveis) - Percentual da meta semanal atingido por filho - Número de tarefas concluídas vs. total de tarefas da semana

Exemplo visual (para 1 filho):

Luna — Semana de 24/03 a 30/03
████████░░  78%  (234 / 300 pontos)
Tarefas: 14 de 18 concluídas

Dados necessários no Supabase:

Campo Tabela / Hook Status
scores por filho weekly_history.scores (JSON) Existe — WeeklyHistory já persiste
max_scores por filho weekly_history.max_scores (JSON) Existe
Total de tarefas concluídas Contagem de tasks com status = 'closed' na semana Existe via summariesByChild.counts no useWeeklyTasks
Total de tarefas criadas Contagem total de tasks na semana por filho Existe
Meta semanal por filho profile_week_goals.goal_percent Existe

O que precisaria ser criado: nenhum dado novo. Tudo existe. Falta apenas a tela que os apresenta.

Bloco 2 — Painel Emocional Agregado

O que o pai vê: Distribuição de como o filho se sentiu ao longo da semana, dia a dia. Para cada dia da semana, um indicador visual de qual humor predominou nas tarefas concluídas.

Exemplo visual:

Como Luna se sentiu essa semana:
Seg  Ter  Qua  Qui  Sex  Sáb  Dom
 😊   😊   😐   😢   😊   —    —

Nota: o traço (—) indica dia sem tarefas concluídas.

Dado adicional: percentual semanal de cada humor.

😊 Feliz: 60%   😐 Neutro: 25%   😢 Difícil: 15%

Por que isso importa para o pai: o dado emocional agregado transforma informação individual (tarefa por tarefa, visível no PendingReviewsPanel) em padrão semanal. Um filho que teve 3 dias difíceis seguidos — dado invisível na interface atual — fica visível como padrão quando apresentado como calendário semanal.

Dados necessários no Supabase:

Campo Tabela Status
reaction por tarefa (😊/😐/😢) tasks.reaction Existe — preenchido na aprovação parental
carinha por tarefa tasks.face Existe — preenchido pela criança
Data da tarefa tasks.date Existe
Aggregação por dia por filho — Não existe — precisa ser calculado no frontend ou persistido

O que precisaria ser criado: - Query que agrupa tasks por child_id + date + reaction para a semana encerrada - Cálculo da distribuição percentual de humores na semana - Ou persistência desses dados em weekly_history.emotional_summary (JSON) — campo novo

Recomendação: calcular no frontend a partir dos dados existentes de tasks — sem novo campo de banco para o MVP desta tela.

Bloco 3 — Destaque da Semana

O que o pai vê: Um insight gerado pelo produto — 1 frase — sobre o desempenho da semana. Não é dado bruto. É uma observação que o produto gera a partir dos dados.

Exemplos de insights por padrão:

Padrão detectado Insight exibido
Filho concluiu tarefas nos 5 dias úteis “Luna foi consistente nos 5 dias — isso é raro e valioso.”
Primeira semana com 100% de meta atingida “Primeira semana com meta atingida. Isso vai ficar no histórico.”
Taxa de conclusão caiu vs. semana anterior “Luna concluiu menos tarefas que semana passada. Vale conversar?”
Nenhuma tarefa concluída em 2 dias seguidos “Quarta e quinta sem tarefas concluídas. Pode ser cansaço — ou a missão está difícil demais?”
Todos os dias com humor positivo “Luna sinalizou que estava bem a semana toda. Missões no ponto certo.”
Mais de 50% das tarefas com humor triste “Muitas missões foram difíceis. O nível está adequado para a Luna?”

Lógica de geração: regras determinísticas no frontend, sem IA. Cada insight é uma condição if sobre os dados da semana. Prioridade: o insight mais relevante é exibido; nunca empilhar dois.

Dados necessários: os mesmos dos Blocos 1 e 2. Nenhum dado adicional.

O que precisaria ser criado: - Biblioteca de templates de insights com condições associadas (src/lib/weeklyInsights.ts) - Lógica de seleção do insight mais relevante

Bloco 4 — Ação Sugerida

O que o pai vê: Uma ação concreta que o produto sugere para a semana seguinte, derivada do insight do Bloco 3.

Exemplos:

Insight (Bloco 3) Ação sugerida
Muitas missões difíceis “Dever de casa teve muitas carinhas tristes — vale conversar com a Luna?”
Dias sem conclusão “Que tal criar uma missão mais curta para as quartas-feiras?”
Semana ótima “Tudo certo! Quer adicionar uma missão nova essa semana?”
Meta não atingida “A meta foi 78%. Que tal ajustar para 70% por enquanto?”

Formato: 1 frase + 1 botão de ação (ex: “Abrir Settings”, “Criar Nova Missão”, “OK, vou conversar”). O botão “OK, vou conversar” não faz nada — é apenas fechamento do modal com intenção registrada (opcional: log de intenção para métricas futuras).

Dados necessários: derivados dos Blocos 1, 2 e 3. Sem dados adicionais.

O que precisaria ser criado: - Mapeamento insight → ação na mesma biblioteca de weeklyInsights.ts - Componente de botão de ação que navega para a tela correta ou fecha o modal

Bloco 5 — Recompensa

O que o pai vê (quando meta foi atingida): Celebração visual — animação simples, mascote Blip, mensagem de parabéns — seguida da exibição da recompensa definida.

Exemplo:

[animação mascote Blip]
Luna atingiu a meta da semana!

Recompensa: Sorvete especial depois da escola

O que o pai vê (quando meta não foi atingida): Sem celebração. Apenas os dados dos Blocos 1–4 sem destaque emocional. A falta de celebração é a comunicação — não há mensagem de “você não conseguiu”, pois isso é o contrário do tom Blip.

Dados necessários:

Campo Tabela Status
Tipo de recompensa semanal profile_goal_settings.default_week_reward_type Existe
Título/valor da recompensa profile_goal_settings.default_week_reward_title / default_week_reward_amount Existe
Meta semanal por filho profile_week_goals.goal_percent Existe
Score da semana weekly_history.scores Existe
Max da semana weekly_history.max_scores Existe

O que precisaria ser criado: - Lógica de comparação (score / max_score) >= goal_percent - Componente de celebração com animação (pode ser CSS puro ou lottie — decisão de UX) - Exibição da recompensa configurada

Mapa de dados: o que existe hoje vs. o que precisa ser criado

Bloco Dado Existe Precisa criar
1 — Desempenho Pontuação semanal por filho Sim (weekly_history) Tela
1 — Desempenho Taxa de tarefas concluídas Sim (tasks.status) Tela + query
2 — Painel emocional Humor por tarefa Sim (tasks.reaction) Aggregação + tela
2 — Painel emocional Distribuição percentual Não Cálculo no frontend
3 — Destaque Insight gerado Não weeklyInsights.ts + lógica
4 — Ação sugerida Ação derivada do insight Não Mapeamento + componente
5 — Recompensa Tipo e valor Sim (profile_goal_settings) Lógica de comparação + componente
5 — Recompensa Celebração visual Não Animação + componente

Resumo: os dados existem. O que não existe é a camada de apresentação e interpretação. Essa tela é, do ponto de vista de banco de dados, de baixo custo — nenhuma migração necessária para o MVP desta tela.

O que esta tela NÃO é

  • Não é relatório de BI — sem gráficos de série temporal, sem comparações entre filhos, sem benchmarks externos
  • Não é dashboard permanente — aparece uma vez por semana, não fica disponível como tela principal
  • Não é punição camuflada — quando a meta não é atingida, não há mensagem negativa, apenas ausência de celebração
  • Não é opcional para o produto — sem encerramento visual do ciclo semanal, não há loop de retenção

Notas de implementação (para referência futura do Arquiteto)

Esta spec não define implementação. As notas abaixo são orientações de contexto para quando a tarefa for para desenvolvimento:

  • O modal deve ser verificado na montagem da tela Index — comparar lastWeekResumeSeen (localstorage) com o weekStart atual para decidir se exibe
  • Os dados de tasks da semana encerrada precisam vir de um query com range de datas [weekStart - 7, weekStart - 1]
  • A aggregação emocional pode ser feita no mesmo hook useWeeklyTasks com referenceDate na semana anterior
  • O componente de celebração deve usar o SVG oficial do mascote Blip (liberado por Bruno — ver decisoes_produto.md, 2026-04-01)
